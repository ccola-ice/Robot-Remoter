# 机器人遥控通信协议：保留 RC v1，新增 RT v1 遥测

本轮交付的是**独立遥测编解码器及可测试的协议约定**。现有 RC v1 控制帧、无线驱动和接收端行为保持兼容。接收端遥测采样/发送、NRF 回传通道、遥测聚合与 GUI 有效性显示仍待接入，当前产品不会因新增头文件自动收到机器人遥测。

代码：`1_App/robot_telemetry_protocol.h`。测试：`7_Test/host/telemetry_protocol_test.c`，运行 `py -3 7_Test/host/run_telemetry_protocol_tests.py`，可在脚本后指定 GCC 路径。实现为本项目独立设计，没有复制参考项目的协议代码。

## 1. 现状与兼容边界

- `robot_control_protocol.h` 已实现 RC v1：固定 32 字节、整数大端、CRC16、序号、使能标记、X/Y、目标航向、速度上限及六个数字输入。
- `control_link.c` 每 20 ms 尝试发送，NRF ACK 超过 150 ms、输入陈旧、离开控制页、低电压或无线配置变化均触发停机/重新解锁流程。`TX_DS` 是无线硬件应答，不证明接收端应用接受或执行控制。
- `.repair-receiver/1_App/receiver_safety.h` 是本工作区接收端修复副本：200 ms 控制超时；IMU 不健康时停机；新会话先接收 STOP；重复/旧运行帧不续命。旧 STOP 仍停机，但不刷新最后接受序号和时刻。此副本不等于用户实板已烧录的版本。
- `platform_nrf.c` 的旧演示字段 MQ/LIGHT 不是机器人遥测格式；`GuiRobotTelemetry` 和 `menu_robot_telemetry_update()` 已有显示入口，但没有数据接收生产者。其单一 `link_online` 不足以表达分类型过期。
- 两端代码默认 RF_CH=40、5 字节地址 `34 43 10 10 01`、载荷 32 字节；遥控器提供频道/速率配置，接收端副本仍是固定初始化。参数匹配、真正烧录版本、模块能力都需要在下一轮双端接入时确认。

### RC v1 保持原样

| 字节 | 意义 |
| --- | --- |
| 0–9 | 全零，避免被早期旧协议当作有效运动指令 |
| 10–12 | ASCII `RC`、版本 1 |
| 13 | bit0=armed，其余必须为零 |
| 14–15 | uint16 sequence |
| 16–19 | int16 X、Y，各 -1000..1000 |
| 20–21 | int16 相对本次使能时航向的目标偏移，0.1°，-1800..1800；不是转向角速度 |
| 22–23 | uint16 limit，0..1000，接收端配置轮速上限的千分比 |
| 24–25 | uint16 digital，bit0..5=DCH1..6，1 表示低电平有效 |
| 26–29 | 全零 |
| 30–31 | CRC16，高字节在前 |

未使能时 X/Y/航向/limit 必须全零；使能时 DCH1 必须有效且 limit 非零。此轮不改变校准、归一化、目标航向控制方式或接收端轮速限制，也不把航模 PWM/PPM、参考项目控制帧直接移植到机器人。

## 2. RT v1 公共封装

RT 是**另一种帧**，不挤占 RC 的保留字段。所有帧恰好 32 字节，超过或不足均拒绝；所有多字节数值大端、有符号数采用二进制补码。禁止直接传输 C 结构体、指针或 float。

| 字节 | 类型 | 含义 |
| --- | --- | --- |
| 0–1 | ASCII | `RT` |
| 2 | uint8 | 版本 1；未知版本整帧拒绝 |
| 3 | uint8 | type：1 状态、2 运动、3 本地位置、4 GNSS |
| 4–5 | uint16 | telemetry sequence，**每个 type 独立**递增 |
| 6–7 | uint16 | 接收端最后接受的 RC 控制序号 |
| 8–11 | uint32 | session，非零启动/坐标系会话代号，规则见下节 |
| 12 | uint8 | 该 type 的字段有效位 |
| 13 | uint8 | bit0=最后接受 RC 序号有效；bit1..7=0 |
| 14–29 | 16 B | type 对应载荷 |
| 30–31 | uint16 | CRC16/CCITT-FALSE，对字节 0..29 计算 |

CRC 参数为 poly=0x1021、init=0xFFFF、refin=false、refout=false、xorout=0；`123456789` 的校验值 0x29B1。CRC 用于检测传输/编码错误，不提供设备身份认证或防伪造能力。

所有保留字节、未知有效位必须为零。**无效字段必须编码为零**；解码器拒绝有效位与残留数据冲突，避免陈旧数值被误当作测量结果。零值本身并不代表无效，有效位允许表达 0 V、0% 或经纬度 (0,0)。发送端应在越界、未标定、传感器缺失或采样过期时清有效位，不能夹紧成看似可信的测量值。

`robot_telemetry_encode(out, length, frame)` 和 `robot_telemetry_decode(bytes, length, out)` 返回 1 表示成功；失败返回 0 且不修改输出对象/缓冲区。所有失败路径先检查指针与显式长度，再访问帧数据。头文件仅负责格式/语义校验；重复帧、会话准入、缓存生命周期属于下一轮聚合器职责。

## 3. 四种载荷

### type 1：接收端状态

| 字节 | 数据 | 有效位 |
| --- | --- | --- |
| 14–15 | uint16 机器人供电电压，mV | bit0 |
| 16 | uint8 电量，0..100% | bit1 |
| 17 | uint8 状态：0 BOOT_LOCK、1 STOPPED、2 READY、3 ARMED、4 FAILSAFE | bit2 |
| 18–19 | uint16 故障位：bit0 控制链路、bit1 IMU、bit2 电池、bit3 急停、bit4 电机、bit5 启动检查；其余零 | bit2 |
| 20–21 | uint16 距最后接受 RC 的时间，ms，超过 65535 饱和 | bit3 |
| 22–23 | uint16 应用层拒绝帧计数，模 65536 | bit4 |
| 24–25 | uint16 观察到的 RC 序号缺口累计，模 65536 | bit4 |
| 26–29 | 全零 | — |

公共 bit0 未置位时 accepted-control-sequence 必须为零，状态 bit3 也必须清零；ARMED 需要公共 bit0 有效。accepted-control-sequence=0 是合法序号，不能拿它当“尚未收到”的哨兵。

状态是接收端应用的实际安全状态，不直接复制遥控器请求。故障位可以同时置位，未知故障需要版本升级，不能借用保留位。电压来自机器人端测量，本机电池 PC3 ADC 不得填在这里。没有可靠 SOC 算法时只发送电压，将电量 bit1 清零。

“最后接受”指经过协议校验、序号检查和接收端安全处理后被纳入当前会话的最新 STOP/RUN 控制；被拒绝的运行帧、旧/重复帧不能刷新。旧 STOP 造成停机时可改变状态，但保留原 accepted-control-sequence 和 age。这个序号证明应用处理过命令，**仍不能证明电机/机构已完成动作**。

拒绝计数统计已到 MCU 却未纳入新控制序列的帧，包括格式错误、旧/重复序号、安全条件不满足；旧 STOP 即使触发停机也不推进序列，可计为拒绝。序号缺口只在已建立控制序列且接受新的序号时累计 `delta-1`，半圈以外/超时重建基线不累计。它不是无线丢包率：发送端调度中断、应用拒绝、重启都可能形成缺口。无线重发次数另行诊断。

### type 2：运动和惯性测量

| 字节 | 数据 | 有效位 |
| --- | --- | --- |
| 14–15 | int16 车体前向有符号速度，mm/s | bit0 |
| 16–21 | int16 roll、pitch、yaw，0.1°，各 -1800..1800 | bit1，三个值同时有效 |
| 22–27 | int16 车体 X/Y/Z 线加速度，mm/s² | bit2，三个值同时有效 |
| 28–29 | 全零 | — |

车体坐标约定 X 向前、Y 向左、Z 向上；角度为右手旋转、姿态采用 yaw-pitch-roll（Z-Y-X）。yaw 相对本会话初始方向；roll/pitch 相对重力水平面。速度正向为车体 X 正向，不能拿未标定的编码器计数直接充当 mm/s。线加速度应已去重力；只有原始比力时清 bit2，不能混用量纲。后续接入方负责将当前传感器安装方向转换到此约定。

### type 3：本地位置

| 字节 | 数据 | 有效位 |
| --- | --- | --- |
| 14–25 | int32 X、Y、Z，mm | bit0，三个值同时有效 |
| 26 | frame=1：本会话建立时的本地固定坐标系 | 随 bit0；无效时为 0 |
| 27–29 | 全零 | — |

原点为本会话建立的位置；+X 为初始车体前向、+Y 为初始左向、+Z 向上，坐标系建立后不随机器人转动。该坐标不是 GNSS 经纬度，不是每次采样都重设的车体系。重置里程计原点必须建立新的 session 并使聚合器清空所有分类型缓存。没有可靠里程计/定位解时整组无效。

### type 4：GNSS

| 字节 | 数据 | 有效位 |
| --- | --- | --- |
| 14–17 | int32 纬度，1e-7°，-900000000..900000000 | bit1 |
| 18–21 | int32 经度，1e-7°，-1800000000..1800000000 | bit1 |
| 22–25 | int32 海拔，mm，平均海平面基准 | bit2 |
| 26 | fix=0 无定位、2 二维、3 三维 | bit0 |
| 27 | uint8 卫星数 | bit0 |
| 28–29 | 全零 | — |

经纬度有效必须同时有有效 fix>=2；海拔有效必须有有效 3D fix。可报告“卫星数 8、无定位”，但不能带有效经纬度/海拔。全球位置与本地位置分帧，避免在一个 16 字节载荷中牺牲量纲或靠浮点压缩塞入全部数据。

## 4. 序号、启动、回卷与过期

1. **接收端会话。** session 使用持久化单调递增 uint32 代号，启动或主动重置本地坐标原点时先可靠提交下一个值，再发布遥测；0 保留不用，0xFFFFFFFF 后跳到 1。持久化使用项目已有可靠存储机制实现，不能每个数据包写 Flash。本轮 codec 不实现该存储。若不能保证代号更新，应保持遥测不可用，不能固定填 1 后声称支持重启识别。
2. **遥控器初始化。** 聚合器起始为“未收到”，所有有效位清零、每类 `seen=0`。选定设备并清空 NRF RX FIFO 后，只允许校验通过的 STATUS 帧建立初始 session；收到新 session 的 STATUS 时清空旧会话全部缓存/序号/计数基线。新 session 比较采用 uint32 半范围差值；旧会话帧不能切换当前 session。相同 session 的新类型可独立建立首帧序号基线。中断不得直接把半更新对象给 GUI。
3. **每类序号。** 每生成一个新的该类快照递增一次 uint16 sequence；硬件重发或再次排队同一快照沿用旧序号。已见类型只接受 `delta=(uint16)(next-previous)` 满足 `0<delta<32768` 的新帧；相同/倒序/恰好半圈不刷新数值、计数或新鲜度。65535→0 正常。连续离线或接收端暂停足以超过半序号空间时，不得擅自按旧序号恢复；通过显式重新连接/会话初始化重建基线。
4. **本地丢包观察。** 每类 gap=`delta-1` 单独累计；它表示遗漏的遥测快照，而不是 RF 底层重发失败率。第一次/新 session 不计算 gap。STATUS 内两项计数同样模 65536，消费者只在同一 session、采样间隔足够短时做模差，无法确定是否跨越多次回卷则标记未知。
5. **新鲜度。** 仅校验通过且通过会话/序号准入的新帧记录本机 `received_ms`。STATUS 1000 ms、MOTION 300 ms、POSITION 1000 ms、GNSS 2000 ms 到期；`age >= timeout` 即失效。使用 uint32 毫秒减法处理时钟回卷；不能让缓存跨过完整 32 位时钟周期继续有效。新状态帧不能给旧姿态/GNSS 续命，CRC 错帧/重复帧也不能续命。
6. **采样和排队。** 接收端只发布有时效保证的快照：状态/位置/GNSS 采样到入队不超过 200 ms，运动不超过 50 ms；传感器字段超时即清有效位。应用队列保留最新快照，发送层控制排队年龄，断链时丢弃旧队列。RT v1 不携带同步时钟或完整采样时间，所以遥控器 freshness 只能衡量“新帧抵达后时间”，不能独立证明端到端采样时延；未来若无法约束队列则需新版本加入采样时间。

公共 accepted-control-sequence 只在该遥测快照时刻有效。四类快照可能略有错时，聚合器不能因后到的旧采样类型把接受序号回退；使用同一 RC 会话中的半范围序号比较。遥控器自身重启/控制序号重新建基线后，要清空待关联历史，等待接收端 STOP 重建及后续新 STATUS，再把序号与新发送记录关联。不能仅用“刚发送的序号等于收到的序号”推断动作完成。

`robot_telemetry_sequence_newer()`、`robot_telemetry_session_newer()` 和 `robot_telemetry_is_fresh()` 提供基本运算；**它们不替代上述聚合器状态机**。特别是 `is_fresh()` 不能拿全零初始化的时间戳当成已收到样本，调用者必须先检查 `seen`。

## 5. NRF 接入路线与接收端升级

首选验证 ACK payload 通道：让遥控器保持 PTX、机器人保持 PRX，在后续控制包的 ACK 中附带已经生成的 RT 快照。Nordic 的产品规范定义 ACK payload 和动态载荷能力；实际 E01 模块的芯片/兼容实现与寄存器行为仍需实测。[Nordic nRF24L01+ Product Specification](https://docs-be.nordicsemi.com/bundle/nRF24L01P_PS_v1.0/raw/resource/enus/nRF24L01P_PS_v1.0.pdf)

接入时必须双端验证 FEATURE/EN_ACK_PAY/EN_DPL、DYNPD、RX 载荷宽度读取、FIFO 排空、IRQ/TX_DS/RX_DR 同时到来的处理，以及各速率下 32 B ACK 的重发间隔和最坏占用时间。现有 `NRF_TxPoll()` 只报告传输结果，不能擅自认为已经实现 ACK 数据消费。

ACK 内装的是预先排队的应用快照，通常反映此前接受的控制。不能将本次无线 ACK 自动解释为本次命令已被应用处理。即使以后所有遥测项都正常，也保留接收端独立的控制超时、IMU 门控和硬件看门狗。

建议初始发布预算 STATUS 10 Hz、MOTION 20 Hz、POSITION 5 Hz、GNSS 2 Hz，共 37 个新快照/秒；这只是待台架确认的调度起点。未知/未实现的传感器不虚构数据；可发送该类 valid=0 的新帧显式撤销旧数据显示。优先 STATUS，数据缺失不能阻塞 50 Hz 控制服务。若模块不支持可靠 ACK payload，应另外设计严格限时的双端收发时隙，单独验证 150/200 ms 故障边界后再启用；不能把现有阻塞式收发演示函数塞进控制循环。

实施顺序：

1. 在接收端接入相同 codec，将真实安全状态、已接受序号、传感器单位转换与 session 持久化落实；生产者必须给出实际采样有效性。
2. 双端实现并台架验证回传链路，保持 RC v1 不变，默认回传功能关闭，确认后再开启。不要只升级一端的射频寄存器就投入控制。
3. 遥控器增加每类型缓存、session/序号准入及过期处理，将 GUI 结构扩展为分字段/分组有效；未实现的字段显示 `--`。现有 `GuiRobotTelemetry` 只有总在线位，不能直接零填缺失字段后标 ONLINE。
4. 通过真实断链、双端分别重启、旧帧重放、序号/时钟回卷、FIFO 堵塞和传感器停止刷新测试后，再将遥测健康用于辅助提示。需要改变控制安全条件时另做明确的两端设计与验证。

## 6. 本轮验证

主机测试以真实头文件编译，C99、`-Wall -Wextra -Werror -pedantic`：四类独立 golden vector 与边界有符号数；全帧 1024 个单比特破坏；短/长/空指针输入；重新计算正确 CRC 后的非法版本/type/保留位/数据范围/有效性矛盾；所有拒绝路径不修改输出；序号/session/毫秒计数回卷；RC/RT 互不误识别。

另已使用项目的 ARMCC 5 对 Cortex-M4.fp、little-endian、C99、Microlib、O1 配置做目标编译检查：wrapper 实际调用编码、解码及三个序号/时间辅助函数，成功生成对象文件，无错误或警告。wrapper 与对象放在 EIDE 工程 `build/reference-study/hardware/telemetry_arm_smoke.*`，未加入固件运行路径。既有控制协议/安全主机测试同样通过。

这些测试证明 codec 的软件行为，不代表射频链路、实际接收固件、传感器量纲或机械执行通过验证。
